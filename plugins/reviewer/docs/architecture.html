9. 白話版：reviewer 看哪些面向、跟外面的做法比、到底有沒有效

這一節不講 script 和 schema。先說 reviewer 在替你看什麼，再對照 Anthropic、CodeRabbit / Greptile、學術研究、spec-driven 工具各自怎麼做，最後對三個 skill 各下一個判斷：有沒有達到當初的預期。

9a. 它看哪些面向

審 spec（/reviewer:spec、spec-dual 共用，7 個角度）
範圍與邊界這份東西要做什麼、明確不做什麼？有沒有偷渡範圍。
完整性與邊角空值、失敗、權限、極端輸入有沒有被寫到。
任務與完成條件每個 task 做完怎麼算做完？能不能驗。
平台與工具可行性要用的庫、API、環境真的辦得到嗎。
設計合理性資料流、狀態、錯誤處理站得住腳嗎。
內部一致性proposal、design、tasks 三份互相講的是同一件事嗎。
跨單元組合（需要時）幾個獨立的 spec 一起實作時會不會互相打架。
審實作（/reviewer:result，3 個角度）
Spec 覆蓋spec 說要做的，diff 裡每一條都有對應嗎？checkpoint 有勾嗎。
穩健性與安全沒驗的輸入、吞掉的錯誤、競態、注入、資源沒釋放。
正確性與邏輯邊界差一、型別混用、舊值沒更新、兩個檔案對同一件事算法不同。
再加一個可選的第二引擎（-c）：Claude 的 /code-review 或任何 review skill，把它的 finding 併進同一張表。

一句話：spec 階段抓「想錯、漏想、互相矛盾」，result 階段抓「做錯、沒做、做了 spec 沒說的危險事」。每個角度一個獨立的子代理只帶自己的簡報，再由程式合併，這是整個設計的核心賭注。

9b. 跟外面的做法對照

誰 / 什麼他們怎麼做、解決什麼問題reviewer 對應的地方差距
Anthropic Claude Code Review（Team/Enterprise，2026） 四段：Find（多個 agent 平行讀 diff 與周邊）→ Verify（對著程式碼再驗一次，刪掉誤報）→ Rank（去重、依嚴重度排）→ Post。永不 approve / block。內部自報「被工程師標為錯的 finding 不到 1%」。預設只看正確性，不管格式與測試覆蓋。 Find = 多 angle 平行 ✓；Rank = merge 去重 + worst-first ✓；Post = merged.json 與報告 ✓；verdict 只建議不阻擋 ✓；「沒 finding 不代表沒 bug」= 我們的 complete:false 態度 ✓。 1.22.0 補上了 Verify 段（結構對齊）。效果未證明：6 次實跑 79 條全 confirmed，因為 fixture 裡沒有假發現可擋。誤報率仍然沒量過。
商用 PR reviewer：Martian Code Review Bench、Entelligence 2026（CodeRabbit、Greptile、Codex） 用真實 bug commit 重播成 PR 當 golden set 評分。F1 大約 50–65%；recall 47–79% 看 repo。多家小型 seeded 測試顯示跨檔缺陷是共同的盲點。評分方式（一題一 bug vs 每個缺陷都算）會翻轉名次。 我們有自己的 seeded harness（7 個 bug，含 3 個跨檔、1 個埋在 600 行裡），recall 0.86，原 4 題 1.0；跨檔靠 merge 的 head 掃描補到 2/3 種。 規模差兩個量級：7 個合成 bug、一個模型家族、三次。能說「pipeline 沒漏」，不能說「比 CodeRabbit 強」。
學術：CodeX-Verify（4 個專職 agent）、QASecClaw（多 agent 過濾 SAST 誤報） 分工的多 agent 抓得多（76% 命中）但誤報一半；多 agent 當過濾器把 Semgrep 的 F1 從 78 拉到 91。結論：分工提 recall，過濾提 precision，兩段要分開做。 分工段有了（angle 子代理）。 過濾段有了，精度未量：需要埋假發現的 fixture。
學術：多模型投票的「popularity trap」、異質團隊研究（2026） 同源模型投票會把少數正確答案投掉；異質模型有幫助但常輸給最強的單一成員。多樣性比投票機制重要；union 拉 recall、投票拉 precision。 spec-dual 的 Claude + Codex 是異質；合併用 union（任一引擎 MEDIUM+ 就是 blocker），不投票。誤報交給 fixer 的 disposition 和升級給人。 方向對，代價是 fixer 要承受更多假 blocker。「Codex 到底多補了幾條 Claude 漏的」有資料（history 的 engines[]）但還沒算過。
Spec-driven 工具：Kiro、OpenSpec、Spec Kit 把人工審查放在需求與設計兩道門。常見坑：spec 看起來精確其實很淺、自動生成的需求把沒人同意的假設寫成規定、實作後 spec 不會自己更新（drift）、agent 不會均勻注意整個 context、要審的 markdown 太多。 spec / spec-dual = 人工那道門之前的自動門，專打「淺、假精確、互相矛盾」；result = drift 檢查（code 對 spec）；rules 飛輪把反覆出現的坑變成下一次的檢查項。 spec harness 有了（6 seed，首量 0.94）。缺的變成：fixture 小而粗、extra 多；嚴重度一致只有 0.18。
Google：ML 解決 review comment（ICSE-SEIP 2024）、AutoCommenter 衡量標準不是「講了幾條」而是「有多少 comment 真的讓程式碼改了」：7.5% 的 reviewer comment 由 ML 建議直接解決；AutoCommenter 約四成 comment 導致修改。 1.21.0 的 history v3 加了 outcome（fixed / escalated / residual / open），第一次能算這個數字。 OneLegion 第一輪 --fix 有了 12 fixed / 12 escalated；escalated 現在能用 settle-findings 收尾，outcome 才會變成可統計的數字。

9c. 總結判斷：三個 skill 有沒有達到預期

/reviewer:result
有，而且是唯一有數字的

預期：抓到 spec 與實作的落差和隱藏 bug，不重複報。量到的：原 4 個 seed 從 0.75 到每次全中；7 個 seed 0.86，加了查證段後不變；每次 7 條、extra 0；跨檔同構造 2/3 種抓到；600 行裡的 bug 3/3。沒量到的：誤報率。查證段跑了但沒東西可刪，所以「不吃 recall」有證據，「少誤報」沒有。判斷：達到「抓錯、不重複」的預期；「少誤報」有機制、沒證明。

/reviewer:spec
架構到位，第一個數字 0.94

預期：實作前抓出想錯、漏想、矛盾。現在有自己的 seeded harness：6 個埋好的缺陷 3 次平均 0.94，漏的是 proposal 與 spec 之間的矛盾（2/3）。OneLegion 真實 change 一輪 --fix：24 條，12 條文字修正自動補、12 條決定類全部升級給人，沒有 AI 替 AI 補決定。弱點：extra ~15 條/次（部分是沒合起來的重複）、嚴重度一致只有 0.18。判斷：抓得到，抓太多；下一步是 fold 與嚴重度校準，不是 recall。

/reviewer:spec-dual
迴圈邏輯驗證完整，雙引擎的增益沒算過

預期：兩個不同來源的模型互補，自動修到兩邊都乾淨，修不了的升級給人。24 個 harness scenario 證明 union、升級、gate 回歸、引擎死掉的處理都對；研究也支持異質 + union 的選擇。沒做的：Codex 到底多抓了幾條、假 blocker 讓 fixer 多做了多少工。history 裡 10/16–10/19 的 engines 資料已經可以回答第一題。判斷：機制達標，效益待一次簡單的統計。

整體：結構現在完整對齊 Find → Verify → Rank → Post，三個 skill 都有自己的量尺。查證員的判斷：不吃 recall（兩個 harness 共 9 次、0 條真 bug 被刪），但誤報過濾未證明（79/79 confirmed，fixture 裡沒有假發現；簡報也把嚴重度、重複、判斷型發現排除在反證之外）。下一個該做的是埋假發現的 fixture，在那之前不要宣稱誤報率。
